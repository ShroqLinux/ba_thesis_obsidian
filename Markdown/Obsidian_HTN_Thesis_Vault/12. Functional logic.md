
## Functional logic

Both coordination and communication in distributed computing have been extensively researched, Lamport (1978) laid the foundation for logical clocks, "happened before" relation and vector clocks. Same can be said about lower level communication including but not limited to Remote Procedure Calls (RPC) and Remote Method Invocations (RMI) (Tanenbaum and Van Steen, 2017). This shifts the focus from coordination and communication which is relevant to the foundational concepts of distributed computing to the context of how both need to be designed for an architectural concept of a distributed hierarchical-task-network. As an initial approach, it is useful to consider what is generally required for a redundant node-cluster before specifying it further to an HTN.

Firstly, it is to be defined what an expected normal mode of operation must fulfill and which functionality it performs. The second mode of operation is the response to a failure that has occurred during normal operation. In any distributed system, this requires state synchronization across all components in the system. As a start, three system states will be defined: Active, Failure and Standby. 
Active is the expected system behavior in normal operation where input data is received, passed to worker nodes, a result is determined and forwarded as output. Generally in a system's definition (especially complex ones), there are many different failures that are possible, many of which have been extensively researched in the domain of safety-critical systems. Hence it is necessary to define which types of failures will be analyzed here. The scope will be restricted to a node failure, specifically the worker nodes because of the main question in this writing on failure mitigation. The third system state is Standby which would be during system recovery where all other components must wait until normal operation may resume, upon which the system transitions again to Active state.

# System states

In Active state, synchronization is needed at different points during normal operation.
Input data may be received from different sources at varying times and potential delays are also involved. Therefore a synchronization point is defined at the start of the process. The worker nodes themselves may have different execution times until completion of their task. This is the second synchronization point. Then before the output data can be sent forward, a third synchronization point is required from TMR voter resolution to the decision of how the voter result is to be used.

![[Screenshot 2026-10-27 at 11.02.37.png]]

The reason for a second type of resolution is one common flaw with voter resolution. If a majority of the worker nodes' results is equally incorrect, the voter would resolve it as a valid result. This is a common mode failure (CMF) and has been researched thoroughly already. Mitra et al. (2000) describes several techniques to handle common mode failure, one aspect is to include methods that avoid CMF in the design and development process. It is important to mention here that any technique can only mitigate or reduce the effects of a CMF significantly, but cannot remove one entirely. One method is to use design diversity which is also possible with N-version programming, this method was mentioned earlier in the scope reasoning of this thesis (Mitra et al., 2000).

Next is the state of Failure where detection and response need to be defined. In a distributed system, the use of heartbeat messages is a common method for this to determine liveness of a component in the system. One example for this is described in Steen et al. (2025) in Raft where a leader signals its followers by regularly sending messages to tell it is still active and operational. The same logic will be used here where the worker nodes periodically send a message to signal their liveness. A timer expiration can be used if after the last message no further response is received for a defined duration. When the timer has expired, it is assumed that the corresponding node is unresponsive and therefore a failure has occurred. Then other components must be signaled of the failure with a broadcast message to halt current execution.

To transition back to Active state, the system must be resynchronized to a common state for a restart. Hence in Standby state, all components in the system reach a 'starting point' in their program until the node recovery has completed. For this, one signal is broadcasted by the node on its own when it has finished starting up again.

_Note 01/11/26 Component contract and interface definition_

Connecting with the concept earlier from the technical problem definition, each component must be assigned a set of functions they must fulfill and what interfaces they use to work with other components. To do this, the Active state can be analyzed first because it is the expected system behavior where all worker nodes compute a task plan with their task trees.
The dispatcher will be assigned the task of synchronization for the starting and ending keyframes. It first waits for all external data sources to send their data which is to be used as input data. Next step is to forward input data and initial world state to the worker nodes which all would start closely (even if not exactly) at the same time at keyframe sync3. At the ending keyframe sync3, the dispatcher is responsible for the final resolution whether the computed task plan is to be forwarded to the actuator (systems). To do this, it waits for the verified task plans which were checked by the voter.

The second synchronization point occurs at the voter which must wait for the task plans from all three worker nodes and then can proceed to verify whether all nodes are in agreement with each other. To restrict which functions the voter must do, it will only handle verification of the task plans.
