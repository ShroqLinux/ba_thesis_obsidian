In avionics, the domain environment is typically dynamic (e.g. flight conditions) and a system must be able to respond to changes while it is executing. The use case that will be the focus of this thesis is Suppression of Enemy Air Defence (SEAD) (McLaughlin et al., 2018). The domain constraint of avionics necessitates determinism in safety-critical systems. Conventionally, embedded systems in avionics are designed with consideration to dynamic changes that may occur externally. A common challenge in safety-critical systems is component or system failure, which requires foresight in the design phase during development and an approach must be defined to mitigate its effects with recovery and fallback mechanisms. With the increase of artificial intelligence in software systems, it has become important to understand how it can be integrated in safety-critical domains as well. Hierarchical task networks (HTN) is an AI planning paradigm which has the capability of dynamically responding to external events. Software systems in avionics commonly use triple-modular redundancy (TMR) already which creates the possibility to use HTNs with an established redundancy solution.

The goal of a distributed architecture in a broader context is to have some benefit through system capabilities which a single unit solution cannot fulfill. A single hierarchical task network (HTN) system is also a single point of failure (SPOF), this applies to any system that is implemented as only one component. Since the writing is focused specifically on safety-critical systems, the main question is how coordination can be done effectively for a redundantly designed HTN. This entails relevant components, their capabilities and trade-offs for real-world implementations.
As a method of work, some principles from model-based systems engineering (MBSE) will be used to serve as a framework in guiding the process to find a solution concept. As stated just now with the problem of a SPOF, this defines the *why* in this process and *what* the solution must accomplish.

_Note 15/10/26: MBSE method of work, system definition_

The next step is to state *how* the system-level problem of a SPOF can be solved, which is done by introducing triple modular redundancy (TMR). The decision for TMR is rooted in the common use within avionic and other safety-critical domains, this applies to both hardware and software systems. Hence the architecture defines no restriction on a concept level of how TMR is realized in its technical implementation, both software and hardware may be viable depending on the specific system.

Using the model above, it is simpler to define what other components are necessary to use TMR as a part of the process to mitigate a possible failure. Input would come from other systems, e.g. sensors, sub-systems, etc., and needs to be received by the process. The process then passes forward its output to other sub-systems, e.g. actuators. One principle found in best practices can be applied here, by providing each component only with necessary information which it requires for the functions it is defined for. This leads to the next part which is the main question of this architecture - common interfaces and exchange of information.
