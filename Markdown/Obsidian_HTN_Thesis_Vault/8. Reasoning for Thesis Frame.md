# Reasoning for thesis frame

_Note 27/08/26: Verifying once for current framing of scope of aspects which have been included / excluded whether reasoning has been traced already in domain constraints or research sources_

In review with Gemini, many points in the scope of the thesis have already been excluded. I will attempt to phrase a summary of them over here.

The first part is about the core of [[2. Introduction to HTN|HTN]] and which planner is to be used in the framework, the choice here being SHOP2 (existing implementation with GTPyhop) as it uses DFS-style search in the task tree. DFS is a deterministic search algorithm which lines up well with per-node behavior in a cluster of redundant nodes. Hence why heuristic and stochastic planners are being excluded from the scope as they introduce non-deterministic behavior (examples to be added), same goes for randomized planners.

Moving on to network behavior and topology, the only relevant part is that a static cluster will be considered because a close-world state allows for full offline definition at time of design and development for any mechanisms which TMR and HTN requires. Dynamic management or ad-hoc P2P planning introduces unnecessary complexity, deviating from the main question of the thesis.

Connecting this to the topic of communication within the nodes is the possibility of errors in either transmission medium or the message itself even at successful delivery at the recipient. While message delivery is defined as guaranteed between sender and recipient, it is still possible that errors occur on a bit-level due to electromagnetic variance or hardware problems in electronic components, e.g. CPU, RAM, a bus system or other which aren't a fault of the actual transmission itself. The guarantee for message delivery is assumed based on the existing standards for avionic buses, e.g. MIL-STD-1553 which defines mechanisms for retransmission and bit-level correction like parity bits, Manchester II, etc. There won't be further elaboration on this in the thesis.

After this the next topic is on which types of redundancy will be analyzed. Active Spatial Replication is included as it’s a foundational concept used widely in many safety-critical domains including but not limited to avionic, automotive, medical systems. Replication in the form of work splitting and parallelization is excluded as this is meant for speeding up processing time to optimize for processing time with available resources, not for ensuring resilience under typical failures during runtime.

Then looking at which types of redundancy can be found in the hardware level and at the software level, two specific concepts are excluded from the scope. N-version programming is a process topic combined with engineering which is outside of the scope of question. Same goes for design of the software itself which would be close to analyzing verifiable coding guidelines and methods adhering to standard specifications such as DO-178C, ISO 26262 or alike. This would divert the focus entirely into process engineering all the way from requirements definition, testing to formal verification methods. In the scope for the thesis, the only relevant points are in reasoning and briefly mentioning which design aspects follow in principle the standards.

The last part currently excluded are advanced architectures which make use of [[6. Bridge to Redundancy|TMR]] as one component of the redundancy model. Focus will instead be put on concepts from these architectures to a more basic model with cross-domain referencing as method of reasoning.

Then considering the design of the redundancy model, two aspects currently are within defined scope. The first one being Task ID Vector comparator as a voter for a redundant model. This would be one viable approach to have the core of how TMR can be used for HTN. Further ideas to be explored - trade-offs must be analyzed. The second aspect is regarding monitoring and recovery methods as I have described above. This will include heartbeat messages and watchdog timers. As addressed before, the recovery methods will be the next point in research, after which the detailed analysis can be done on characteristics and advantages / disadvantages of the resulting possible design framework.

Further points to add as suggested by Gemini are reasoning why the voter threshold matching won’t be used. Also justify why in degraded DMR shutdown the DMR itself cannot resolve conflict. For the PoC with virtualization it’s necessary to reason why it reflects physical node behavior without needing to run the implementation in real hardware.
