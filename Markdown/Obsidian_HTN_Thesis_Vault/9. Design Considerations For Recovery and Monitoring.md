# Design considerations for recovery and monitoring

_Note 28/08/26: Reviewing some critical points with Gemini Pro_

Following the point of system design and monitoring methods, Gemini did scrutinize how the semantic logic of a watchdog would work. Watchdog timers are useful to determine when a program might be stuck in a loop and must be terminated to avoid indefinite execution times.

The criticism was a fair point on determining how WCET can be calculated considering that most AI planners are difficult to estimate on this because of the vast search space which in some methods (particularly stochastic and heuristic ones) can grow exponentially.

This however is also excluded by design as SHOP2 uses a DFS-style search in the task tree. Its termination for a state “success” of having found a solution is only contingent on finding the first possible solution with a set of tasks irrespective of whether it’s the most efficient one or not. The SHOP planners don’t continue searching or comparing multiple solutions. In addition to this, DFS is a deterministic search algorithm, meaning that an engineer can determine during offline development the true WCET and add a buffer ε to determine the limit required for a watchdog timer. As then added by Gemini, this can be calculated with the number of CPU cycles required for only the longest possible search path for any search tree.
