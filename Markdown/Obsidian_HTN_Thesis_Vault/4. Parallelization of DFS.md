# Parallelization of DFS

This part addresses the second idea of how HTN can be used in a distributed network. The main concept which needs to be analyzed is whether it’s possible to split the decision tree of an HTN across several nodes. SHOP planners use a DFS-style search algorithm from high-level target, or as stated in Nau et al. (2003) it’s compound tasks, down to primitive task level. One possibility would be to split the decision tree among many different nodes, effectively creating sub-trees which are distributed throughout the network assuming a static network of nodes. There are several aspects to consider with this approach. First is which node is used to start the search and whether it’s determined dynamically. The second aspect is how the sub-trees are linked together in case of backtracking requiring a jump to a branch on a different node within the same node cluster. Guaranteed delivery of messaging is assumed within the node cluster.

Two other concepts which are possible are work stealing and stack splitting as well as randomized parallel DFS. In work stealing when a thread finishes its own part in search, it becomes a 'thief’ and steals from the bottom of a currently active thread that’s still executing. Randomized parallel DFS lets multiple threads run concurrently through the same tree; whenever one thread finds a solution, it terminates execution of all other threads (find more information in research on this). Meaning the search is entirely optimized for finding ‘the first solution possible’ rather than finding the most cost-reducing or resource-efficient solution. Randomized parallel DFS would search through the same exact tree on multiple threads but explore different sub-branches (also add source here if it was already researched). Intuitively, as DFS is deterministic, this approach doesn't apply, as searching with DFS on the same tree would be entirely deterministic resulting in a ‘same path’ of search across all threads giving identical execution times for searches. One method to account for this part is by shuffling which child node is explored at a fork point when applicable.

Another possibility that opens up with this is in the case of redundant systems where multiple nodes would be running the same process. This leads to clusters where multiple nodes can be used for both redundancy as well as parallel searches in HTN.

_Note: you can formally restrict the frame of thesis with some fixed assumptions. Static network cluster, guaranteed message delivery, SHOP planner for DFS-style search

Another question that may be relevant is whether the execution environment is treated as a closed-world with total fixed knowledge or if actors must be able to respond to external changes in a dynamic environment - this is more realistic in the context of an aerial system. This may not directly affect the HTN itself or its parallelization but it may affect how actors across different nodes execute the ‘found’ solution from any node.

To avoid too many forks in the road, it’s likely that I need to restrict my solution space to only one of these ideas on what types of parallelization I could write a concept for.
