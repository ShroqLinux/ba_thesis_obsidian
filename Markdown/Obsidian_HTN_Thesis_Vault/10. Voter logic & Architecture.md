# Reviewing Design for HTN Voter

_Note 01/09/26: Reviewing design for HTN voter_

One flaw that AI pointed out was on my idea of how the voter can compare the resulting task set coming from each node within a TMR. The primitive tasks can be assigned IDs but wouldn’t properly account for parameters.

During offline development, it's possible to define the task tree (compound task -> subtasks) which would be searched through using DFS. DFS is a deterministic search algorithm and would lead to the same exact search path every time given one set of input parameters - in the case of SHOP planners this is the initial world state. This may be getting a bit narrow here, what is possible is that the task IDs and the parameters can be passed to a hash function. The voter can match hashes.

Following the use of hashes, two possible designs emerge from this with varying system properties. One hash can be computed with the array of hashes coming from each task plus parameters and pass it to the voter or the voter gets a slightly longer task and compares three arrays of hashes received from each node. The first design would allow for zero overhead as the voter can compute with $O(1)$ the comparison of three hashes and only checks for an equal match. The drawback here is that this doesn’t allow for any diagnostic visibility. If in a redundant cluster of nodes A, B, C the node C were to fail, the voter can determine that C has failed but cannot see where the error occurred in C.

With the second option of sending the arrays of each node to the voter, the complexity changes to $O(n)$ with $n$ number of elements in each array. This would allow the voter to recognize where in the task order an error occurred and in which node. The voter can log this to allow for either real-time diagnosis and error handling or the same offline. On the point of execution of the tasks, the voter can dispatch tasks which have already been verified while succeeding tasks are still in queue to be verified in the case of long plans. One risk here is if there are succeeding tasks which contain faults that cause the subsequent execution to be halted completely.

Because the voter in this design would only be receiving hashes, it cannot pass the actual task set and their respective parameters to the sub-system or nodes that execute these functions. Further analysis must be done to develop a concept which messages must be exchanged for confirmation of task verification and how the task set is passed to actors.

_Note 22/07/26: Functional logic for architecture_

With the voter's constraint on how much information it receives (hashes) or can return for the individual nodes (positive or negative), it only takes the role of a referee. This splits the responsibilities in the architecture into a data plane and a control plane. The control plane logic can be traced to other domains using decentralized management like in SDNs or orchestration methods in cloud computing, e.g. Kubernetes clusters.

Necessary components at control plane level for a hierarchical task network include a dispatcher for the initial state and goal, state monitoring of worker nodes (e.g. heartbeat messages -> timing frequency can be used for watchdog timeout duration definition), the voter per redundant component and a set of actors.

For the data plane, necessary components are the worker nodes running the HTN SHOP task tree and the actors.
