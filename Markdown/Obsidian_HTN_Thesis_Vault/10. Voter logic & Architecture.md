# Reviewing Design for HTN Voter

_Note 01/09/26: Reviewing design for HTN voter_

One flaw that AI pointed out was on my idea of how the voter can compare the resulting task set coming from each node within a TMR. The primitive tasks can be assigned IDs but wouldn’t properly account for parameters.

During offline development, it's possible to define the task tree (compound task -> subtasks) which would be searched through using DFS. DFS is a deterministic search algorithm and would lead to the same exact search path every time when given the same set of input parameters - in the case of SHOP planners this is the initial world state. This may be getting a bit narrow here, what is possible is that the task IDs and the parameters can be passed to a hash function. The voter can match hashes.

Following the use of hashes, two possible designs emerge from this with varying system properties. One hash can be computed with the array of hashes coming from each task plus parameters and pass it to the voter or the voter gets a slightly longer task and compares three arrays of hashes received from each node. The first design would allow for zero overhead as the voter can compute with $O(1)$ the comparison of three hashes and only checks for an equal match. The drawback here is that this doesn’t allow for any diagnostic visibility. If in a redundant cluster of nodes A, B, C the node C were to fail, the voter can determine that C has failed but cannot see where the error occurred in C.

With the second option of sending the arrays of each node to the voter, the complexity changes to $O(n)$ with $n$ number of elements in each array. This would allow the voter to recognize where in the task order an error occurred and in which node. The voter can log this to allow for either real-time diagnosis and error handling or the same offline. On the point of execution of the tasks, the voter can dispatch tasks which have already been verified while succeeding tasks are still in queue to be verified in the case of long plans. One risk here is if there are succeeding tasks which contain faults that cause the subsequent execution to be halted completely.

Because the voter in this design would only be receiving hashes, it cannot pass the actual task set and their respective parameters to the sub-system or nodes that execute these functions. Further analysis must be done to develop a concept which messages must be exchanged for confirmation of task verification and how the task set is passed to actuators.

_Note 24/09/26: Voter resolution on same path & different order_

While DFS would allow for the same path of search when running identical task trees, there is the case where the ordering of tasks doesn't match for a selected solution task set in the individual nodes. This would occur e.g. in SHOP2 where partial ordering is possible as per Nau et. al (2003). The question here is how a voter can resolve this to select one set which is to be passed further to the actuator (systems). One method for this can be by adding a similarity score with a threshold, this method has been extensively researched already and termed as inexact voting (Parhami, 1994) where two objects $x_i$ and $x_j$  are considered equal if their difference $d$ fulfills$$d(x_i, x_j) \le \epsilon \implies x_i \approx x_j$$for a designated threshold $\epsilon$. If the variation or spread is too far apart, the voter resolves by a best of three match and may reject if this design is extended to compare not only two objects $x_i$ and $x_j$, but the total difference $d(x_{\min}, x_{\max})$. A flaw which is introduced by this would occur when two of the three redundant nodes are equally incorrect, e.g. due to software error or hardware error, and the voter resolves falsely as a correct solution because the threshold bound constraint is still fulfilled.
A design concern would be whether the voter comparison can still work if the order in which hashes are received can vary because of varying orders. This can be solved by switching the data structure in which the voter receives the task sets and use a dictionary instead. Earlier an array was described as a possibility, which is still beneficial since arrays are a smaller data structure which is ideal for data transmission to reduce the data bus occupancy necessary for communication between individual components.
The data structure used for communication has no direct design constraint on what other data structure it can be refactored into when processed in the voter itself. If it's more ideal for parsing in the voter, this can be considered for an unordered comparison.
Since the scope is restricted to not use any thresholds in voting, the original SHOP planner excludes this by design because no partial ordering is used. Here the voter need not use any similarity score or any response for a scenario of equally incorrect solutions which can "trick" the voter.

_Note 22/09/26: Functional logic for architecture_

With the voter's constraint on how much information it receives (hashes) or can return for the individual nodes (positive or negative), it only takes the role of an arbiter / referee. This splits the responsibilities in the architecture into a data plane and a control plane. The control plane logic can be traced to other domains using decentralized management like in SDNs or orchestration methods in cloud computing, e.g. Kubernetes clusters.

Necessary components at control plane level for a hierarchical task network include a dispatcher for the initial state and goal, state monitoring of worker nodes (e.g. heartbeat messages -> timing frequency can be used for node liveness state) and the voter per redundant component.

For the data plane, necessary components are the worker nodes running the HTN SHOP task tree and the actuators.

![[control-data-htn.jpg|581]]

The monitor can be designed in multiple ways. One possibility is to use a polling approach where the monitor periodically sends a message to the planner nodes, which then send a response. In this case, the monitor tracks state of response time to determine a timeout. Monitoring of actuator nodes will be excluded to restrict scope focus on planner node redundancy, this means actuators will be viewed as a black box component.
The second possible design is to have all planner nodes periodically send the monitor their heartbeat messages without prior prompting from the monitor, this would be a push-style monitor. This reduces message count which is beneficial to real systems where data bus bandwidths are typically low and only necessary information is exchanged. The monitor then operates on a primary read functionality by tracking state of messages received with a defined timeout duration based on frequency of heartbeat messages. For a frequency $f$, the timeout can be calculated as multiples $n$ of the period $T = \frac{1}{f}$ and $T_{\text{timeout}} = n \cdot \frac{1}{f} = n \cdot T$.
The frequency of the heartbeat messages is strictly constrained at maximum by frequency of transmission of the bus system being used in a real avionic system. Depending on how critical a redundant component is, this must be determined on a case-by-case basis to allocate properly the required bandwidth and occupancy rate per time on a bus.

_Note 23/09/26: Monitor & Dispatcher design_

As the complementary component, the monitor must have a response for a watchdog timer expiration. If designed as a per-redundant-node monitor, this can be used to detect the unresponsive node and send a signal to restart specifically the affected node. This isn't the only possible design here, there are many other variations possible such as signaling the entire cluster that a node is currently unavailable (and restarting or other error-handling), which can be useful for larger systems where other dependent sub-systems would need to use their own fallback mechanism in a case of node failure.

One common problem that occurs in distributed systems is delay and variation in timing between individual components. This has already been extensively researched
