# Bridge to Redundancy

_Note: 03/08/26 Continue on redundant systems

Further research on the topic of HTNs in redundant systems, connecting with concepts from multithreading and synchronization in parallel processing. Main points here are with data distribution and in the case of multi-node systems also with timing synchronization in the case of redundancy - varying execution times even on the same search.   
Another part is with voting systems which are possible for a combination of both aspects. For multiple nodes running the same decision tree, having a voting system allows for a check of systems that are still active vs. those running into consistency problems like solutions not being found or not returning any response at all. This can be connected to functional safety within software design. Depending on the purpose of architecture, a multi-node system can be used with and without randomized parallelization. With randomized parallelization it’s possible to optimize for what I will term here as a “many paths search” to search multiple sub-trees of a tree simultaneously. Without randomized parallelization you can ensure a deterministic search path in a tree with DFS in SHOP planners. In the case of a voting system when using randomized parallelization, the useful criteria would be with a heartbeat message to determine active and inactive nodes. For both scenarios defining a quorum is also required. Here there are a few aspects to consider in what manner redundancy must be designed. The concept must not focus on possible failures in software because those are linked to design issues, instead a later proof of concept may make use of a virtualization technology like VMs or containers to simulate behavior that resembles how hardware would fail in such cases.  
One system attribute that can be looked into here is whether and how a cluster may become resilient to component level failures.

_Note: 05/08/26 Focus further on redundancy in software, analyze existing implementation of parallelized HTN

Redundancy does not directly mean redundancy. What is meant by this is that there are several types of redundancy in distributed computing. Spatial, temporal and information redundancy. Spatial redundancy focuses on physical components. There are two types of replication possible with spatial redundancy. The first one is Active Replication, the second one being passive replication. In active replication you would have all nodes (redundantly designed nodes) processing the same request simultaneously while in passive replication you would have a primary node replicating information to cold standbys. Temporal redundancy is defined as re-executing a program or a re-transmission of data when an error occurs. Information redundancy is defined as adding bits to the data itself. Methods have already been implemented to recover lost data with minimal storage overhead compared to raw data replication. Sources of this I have saved in the HOME directory on MMAIN drive, need to be quoted.  
The question to analyze for me is which aspect is relevant to be added for a distributed HTN with redundant nodes, considering the assumption that data transmission is guaranteed and static cluster, implying there is no need to analyze dynamism in network management.  
Based on Gemini it is sensible to look into papers defining and analyzing the architecture of SHOP2. Study how they handle execution monitoring. These design aspects might also reveal which type of redundancy might need to be added to a distributed HTN.

An important aspect of SHOP2 is that it doesn’t natively have any monitoring capability. This is relevant for any redundant system, e.g. in voting systems or node health states. This kind of monitoring would need to be done by another monitor node or a thread within the working node responsible for monitoring. To connect to an earlier concept, it’s also necessary to analyze how nodes can cooperate with each other, e.g. for termination when a solution is found in randomized parallelization. This transfers over to other aspects which I have previously noted down, such as in redundant nodes running parallely without randomization, the aspect of node management is relevant.  
One goal in the concept is to keep architecture of the node cluster minimal and describe a possible solution with which it’s possible to design several implementations. Having a single point of focus to target on would restrict solution space well enough to still have a significant amount of depth within the topic.  
Diving deeper into the topic of redundancy within node clusters would mean that the relevance of fault tolerance, recovery and task network distribution is key. According to Gemini, some other aspects come here too. One would be latency in recovery time as well as execution time. Network overhead due to cluster management which would occur also in the case of a fixed cluster size because the cluster must still compensate for either execution failures (solution not found) or node failures (stuck in loop, error at runtime, etc.). Another one can be during execution at time of voting if a node does fail, the important part being how one can resolve this scenario, e.g. Triple Modular Redundant nodes and one node fails, here you then only have two functional nodes. However, one cannot resolve the vote if the two remaining nodes are conflicting.

_Note 06/08/26: Further dive into which types of redundant architectures can be used in distributed systems 

During research with Gemini Notebook I dug into the research papers on redundancy in distributed systems. There are several concepts that stood out to me which already are quite aligned with my own concepts. The two first ones are from “distributed and network redundancy models”, splitting and replication. Splitting is defined as dividing a job equally among n servers without any redundancy which would be useful to achieve maximum parallelity but misses the point of mechanism I described earlier. The second one is closely aligned with what I am analyzing, which is replication. Here you run the exact same job replicated over n servers. Which connects with voting systems in DMR or TMR systems and also according Peng et. al (2021) when small jobs have highly variable service time which can occur under heavy loads. One more point to include is the domain. Within avionic systems, you have several redundancy architectures which are not applicable. The network itself stays static and deterministic as per scope while within the network it’s still possible that faults or failures occur (define them properly later). The next point here is to look into the types of architectures which are well suited and have concept-level transfer into HTNs. Here it is relevant to know how workloads can either be spread or replicated within the network.  
One more model of redundancy which I found interesting is sequential / time-plexed TMR where several redundant data threads are processed on a single functional model after which a voting system is used. This mitigates transient faults and has also been implemented on software-level as per Flad et. al (2026) (Note: look further into the example here later). This introduces two possibilities of redundancy where also a combination is possible. Earlier I had thought of an execution model using multiple nodes or a single node with multiple threads running the exact same HTN with SHOP processing the same task set. The model here would utilize multiple processing of the same task set on a single node or thread which can be applicable in resource constrained systems where multiplicity of resources isn’t an option - also the case in embedded hardware - and time sensitivity has a higher margin of tolerance.  
One concept that stood out to me was Dynamic TMR as described in Anwer et. al (2020). The redundant module would run with the logic of “DMR first, TMR when on-demand”. This does address the question how one can ensure redundancy when one module fails. A backup or “inactive” module is activated, a comparator then uses the outputs of the “new” DMR modules. A comparator on its own can only detect a disparity in results but is limited in that it cannot resolve a conflict when the outputs diverge. My question was however stated in the opposite order of having TMR but with a failure which would reduce the redundant module to a DMR. In theory, one could have an “inactive” module ready to use and “restore” TMR to still enable conflict resolution with a voter. Considering resource constraints such as available compute may introduce hardware and performance limitations in this approach, thus restricting at what level of criticality of a module or function  it may be viable.

Another aspect to address at the level of implementation design is what types of communication links or messages are necessary to allow for inter-node information exchange. Two networks which I had already noted before are heartbeat messages to inform the cluster of currently active / healthy nodes. The second one is related to data for search trees, task distribution and termination signals. At a smaller level this can be first addressed within only one program in case of a single process executing a multithreaded, redundant HTN. On the level of network management for a multi-node cluster, similar management concepts may apply but with a different architectural layout. Connecting with the points on redundancy, one relevant point is to define which metrics can be used to evaluate system resilience. This I want to define at a later point when analyzing one example of a possible implementation which serves as a proof of concept.

Note: 13/08/26 Focus more intensely on learning both fundamentals as well as deeper concepts of TMR

Diving deeper on the fundamental architecture of TMR. The two research papers Bonna et. al (2019) and Hamilton et. al (2019) in NotebookLM are focused on two specific architectures that use TMR. This can serve as a glimpse into certain detailed aspects or characteristic behaviors and flaws which TMR has.   
The base of the distributed HTN with SHOP2 can stay on simple TMR as design of decision tree, splitting and voting system make a significant difference. The benefits, drawbacks and tradeoffs with TMR will require consideration when applying to domain constraints for deterministic behavior due to application with avionics. TMR on its own is an N-modular system where N = 3 using a majority vote to mask failures. If any one of these three components were erroneous, the voter simply ignores them and uses the solution of the two remaining components. This can also change depending on how matches are determined, e.g. binary match or threshold match if using floating point values. The type of voter also changes depending on design of implementation both in the software and in the hardware of each component. Software redundancy can be realized by N-version programming to mitigate single software design issues. This however carries an immense cost on a process level as each version requires its own cycle from design, architecture, implementation through to validation, verification, etc. The hardware side carries its own cost as multiple same components are required, e.g. CPU, RAM, persistent storage, communication buses.  
The voter itself poses a single point of failure which can be redundantly designed two, sometimes also making use of TMR on its own. Another variant to solve this is by utilizing voters that can check themselves. The voter will be an interesting point to solve in the context of HTN as comparing solution paths might require an entirely new method of vote. One idea I came up with just now is to make use of a vector comparison. This means each primitive task would be assigned an ID which would be stored to a result vector. The next step would be to take all result vectors of a redundant cluster and run a comparator as a voter on them. Since SHOP2 makes use of a DFS-style search, the deterministic behavior would be guaranteed within each node. Thus leading to an identical set of vectors being compared.  
The goal here isn’t to check whether an optimal path has been found but to check the status of each node’s correctness.

Note: 19/08/26 Expanding further on architectural layout of TMR itself before connecting with HTN

One aspect of TMR that I am currently analyzing and exploring with the help of Gemini is on communication within the nodes of the redundant module. Since timing can vary for processing time and calculation for each node individually, it may be necessary to design a state synchronization depending on what type of TMR is being used. When implemented as a single process with multithreading, thread signaling can be a viable solution (suggestions here from Gemini: condition variables, thread barriers).  
This expands further in two scenarios. If a node is designed redundantly across several processes, another process can act as a sink to pool all outputs and then allow the vote to be determined - this can be the voter itself waiting for all results to arrive before execution. The third one is when the redundancy is laid out across several hardware which can be simulated using a cluster of VMs. Here, another VM would need to be used for voter logic. One of these solutions can be later used in PoC. What is relevant now is how this affects HTN planning.  
The next aspect is about fault tolerance mechanisms with TMR. One which is described in Djambazova et. al (2023) is the use of structural redundancy with the introduction of additional elements into the system. In this design, both active and passive replication can be used either for concurrent execution along with the primary component in case of the former (which is the case for TMR executing three parallel, identical nodes) or keeping cold spares ready which would activate when a primary or currently executing node does fail. For this it is necessary to define detection and monitoring methods such as heartbeat messages. Another tool for monitoring is the use of watchdog timers to time for any nodes that may be stuck in a loop in execution. This can occur in the case of a faulty search during planning.  
These topics address methods of detection and diagnosis. The next part would address how errors can be contained or even corrected, in some cases leading further to recovery methods.
