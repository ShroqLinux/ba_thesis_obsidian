# Monitor, Dispatcher & State Synch Design

_Note 23/09/26: Monitor & Dispatcher design_

As the complementary component, the monitor must have a response for a watchdog timer expiration. If designed as a per-redundant-node monitor, this can be used to detect the unresponsive node and send a signal to restart specifically the affected node. This isn't the only possible design here, there are many other variations possible such as signaling the entire cluster that a node is currently unavailable (and restarting or other error-handling), which can be useful for larger systems where other dependent sub-systems would need to use their own fallback mechanism in a case of node failure. 

_Note 06/10/26: Approaches in literature for monitoring and failure handling

Bonna et al. (2019) describe a mechanism where the voter handles monitoring and, upon receipt of a differing output, assumes a fault in such processor. Here the error-handling is done by sending a signal to the control device to compensate for said fault, in the case of Bonna et al. (2019) this is done with runtime reconfigurable processors (RTRP). This method would be applicable for hardware faults. Another approach has been developed to compensate for hardware faults by dynamically switching to Temporal Software Redundancy (TSR) (Hamilton et al., 2019). A controller monitors the system for consecutive errors in execution to transition between TMR and a lower-power TSR. The difference here is not only in how the system can handle failures, but also which implications it has on resource utilization. TMR requires three physical processors operating concurrently alongside a hardware majority voter while TSR runs on a single processor, thus requiring less power. In avionic systems, this can be useful when hardware failures occur in the power delivery, for the redundant cluster, and power distribution may be constrained.
Both of these approaches need to account for state synchronization in the software and hardware for the new system state when the error-handling has been executed successfully. For the methods using TMR and TSR and the former with RTRP, this has been done through memory (Bonna et al., 2019; Hamilton et al., 2019). The choice here depends on what production cost is viable for the number of hardware components to be used in the redundant cluster. Another factor is how critical a function is, since RTRP also makes of overriding less critical applications when a processor of a higher priority function incurs an error during execution (Bonne et al., 2019). This means systems to which more cost is allocated for the number of processors, and other hardware components (e.g. memory, controllers, etc.), can still utilize non-primary hardware which allows for a better utilization of all resources, rather than keeping an excess of hardware resources on idle.

_Note 05/10/26: State synch and dispatcher design_

One common problem that occurs in distributed systems is delay and variation in timing between individual components. This has already been extensively researched (Lamport, 1978; Tanenbaum & Van Steen, 2017, pp. 298–303). In the context of a TMR-node cluster used in the concept of this architecture, the same applies in variation of time required for processing, calculation of a plan and outbound transmission to a voter for the software side. As for variations and delays introduced by real electronic systems, the number of possible points where delays occur only increases, i.e. bus frequency, transmission frequency by sender(s), electromagnetically induced variations, jitter, propagation time, etc.
Exploring the entire solution space here would be too large and thus needs to be bound by an acceptable within which questions can be addressed on the theoretical side and a subsequent connection of the possible solution space with real-world implications in safety-critical systems and their limitations. The scope is defined to address critical points which can be handled by the dispatcher. The first critical point is receipt of input data, then the verification by a voter and thirdly the transmission of the final task plan to the actuator system(s). If the scope were simplified further to only address the last critical point which was just mention (transmission to the actuator systems), a strict limitation would be introduced in the capabilities of the dispatcher when applied to real avionic systems. To reduce the number of hardware components, there cannot be a central server or alike to monitor other subsystems which this architecture is dependent on. This functionality can be added to the dispatcher to verify if these subsystems are providing data correctly. In a simple form this can be designed as a read-only check where the dispatcher verifies if it is receiving a message by each of its required sources, which can be a heartbeat message or only the input data which then must be forwarded to the worker nodes. Another addition can be connected to the protocol TCP where an explicit ACK is sent to the sender. This is also found under MIL-STD-1553C, as receipt and validation of messages are confirmed by using the Status Word. Both acknowledgements are required on two different levels since the former is as defined by the ISO/OSI seven-layer model at the transport layer while the latter is relevant for the physical and data link layer.
