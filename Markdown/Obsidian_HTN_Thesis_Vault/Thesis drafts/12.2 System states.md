The reason for a rejection of the voted result is one common flaw with voter resolution. If a majority of the worker nodes' results is equally incorrect, the voter would resolve it as a valid result. This is a common mode failure (CMF) and is defined by Hodson et al. (2024) as a failure that occurs due to a single event, design defect or violation of other independence assumptions. Mitra et al. (2000) describe several techniques to handle common mode failure, one aspect is to include methods that avoid CMF in the design and development process. It is important to mention here that any technique can only mitigate or reduce the effects of a CMF significantly, but cannot remove one entirely.

Following the principle of mitigating CMF in the design process, one choice will be proposed here by introduction of a rule set which in the diagram above was labeled as 'other resolution'. A basic rule set can be defined following the logic of how SHOP works. Because tasks are ordered into their sequence of execution, a check can be defined per pair of any subsequent tasks A and B. If B is allowed to follow after A, then a 'pass' is determined. In the case of a task A before B, where B is must not follow after A, a 'fail' is determined.
Repeating the same input would not yield a different result however, which is also this method's limitation because of DFS' deterministic behavior. The wrong majority still persists with this design choice and cannot be caught with this rule set. Due to definition of the scope focused on node failure and system synchronization, the handling of an incorrect plan will be kept simple as discarding of the result.

Next is the state of Failure where detection and recovery need to be defined. In a distributed system, the use of heartbeat messages is a common method for this to determine liveness of a component in the system. One example for this is described in Steen et al. (2025) in Raft where a leader signals its followers by regularly sending messages to tell it is still active and operational. The same logic will be used here where the worker nodes periodically send a message to signal their liveness. A timer expiration can be used if after the last message no further response is received for a defined duration. When the timer has expired, it is assumed that the corresponding node is unresponsive and therefore a failure has occurred. Then other components must be signaled of the failure with a broadcast message to halt current execution.

To transition back to Active state, the system must be resynchronized to a common state for a restart. Hence in Standby state, all components in the system reach a 'starting point' in their program until the node recovery has completed. For this, one signal is broadcasted by the node on its own when it has finished starting up again.
