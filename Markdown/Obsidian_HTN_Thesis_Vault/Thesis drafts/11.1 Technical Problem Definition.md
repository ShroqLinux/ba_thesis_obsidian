
As a method of work, some principles from systems engineering will be used to serve as a framework to guide the process to find a solution concept. The main focus of systems engineering is to focus on the system as a whole. It is relevant to consider which interactions take place both with external systems as well as internally in the system that is in focus. Other external factors are the customer's (or user's) needs, interfaces, capabilities of the user and more which must be included in a system's design. One approach of systems engineering is the V-Modell which encompasses many steps from the definition of requirements to high-level design, detailed design and on the right side system verification and validation. These stages will also be used here as a reference. (Kossiakoff et al., 2020)

The first question considers what is actually to be solved for with the design and which aspects have been previously developed. This follows the principle in requirements engineering at the left side of the V-model and is a start for problem and target definition.
Both coordination and communication in distributed computing have been extensively researched, Lamport (1978) laid the foundation for logical clocks, "happened before" relation and vector clocks. Same can be said about lower level communication including but not limited to Remote Procedure Calls (RPC) and Remote Method Invocations (RMI) (Tanenbaum and Van Steen, 2017). This shifts the focus from coordination and communication which is relevant to the foundational concepts of distributed computing to the context of how both need to be designed for an architectural concept of a redundantly designed hierarchical-task-network. As an initial approach, it is useful to consider what is generally required for a redundant node-cluster before specifying it further to an HTN.

Firstly, it is to be defined what an expected normal mode of operation must fulfill and which functionality it performs. The second mode of operation is the response to a failure that has occurred during normal operation. In any distributed system, this requires state synchronization across all components in the system. As a start, three system states will be defined: Active, Failure and Standby. 
Active is the expected system behavior in normal operation where input data is received, passed to worker nodes, a result is determined and forwarded as output. Generally in a system's definition (especially complex ones), there are many different failures that are possible. Hence it is necessary to define which types of failures will be analyzed here. The scope will be restricted to a node failure, specifically the worker nodes because of the main question in this writing on failure mitigation. The third system state is Standby which would be during system recovery where all other components must wait until normal operation may resume, upon which the system transitions again to Active state.

For functional logic, the basis for TMR is to use a voter to mask faults. One principle found in best practices can be applied here by providing each component only with the necessary information that it requires for the functions it is defined for. This leads to the next part, which is the main question of this architecture - common interfaces and exchange of information.
